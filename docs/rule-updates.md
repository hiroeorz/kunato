# Daily rule updates and version compatibility

How the managed rule set travels from this repository to a running Kunato, and
how the engine stays safe when the rule set and the installed binary do not come
from the same version. `README.md` ("Rule set format compatibility") states the
policy; this document is the full picture: the two update streams, the failure
mode they can run into, the guards that prevent it, what an operator sees, and
how a new rule construct is released.

```text
rules.example.yaml ──► dist/rules.yaml ──► download ──► validate ──► atomic swap ──► hot reload
   (daily agent,           (+ .sha256)      rules_update  whole set   /var/lib/kunato   ArcSwap
    coverage work)          on main                        │           /rules.yaml
                                      ▲                     └─ reject: keep previous rules,
                        scripts/check-rules-compat.sh         log + counters, retry in
                        builds the newest v* tag and          min(interval, 10 min)
                        validates the published file
```

## Two streams that move independently

| Stream | Source | Destination |
| --- | --- | --- |
| Rule set | `rules.example.yaml` → `dist/rules.yaml` + `.sha256` on `main`, regenerated by `scripts/update-dist-rules.sh` after every rule change | `/var/lib/kunato/rules.yaml` on every install with `rules_update.enabled` |
| Binary | `v*` release tags built by `.github/workflows/release.yml` | installed by `scripts/install.sh` from `releases/latest` |

The published rule set is always the newest one, while an install keeps whatever
binary it was installed with, so "new rules, older binary" is the normal state,
not an exceptional one. That is the reason for everything below.

## Why a mismatch matters

Rules are a schema, not free-form text: categories, rules, match fields, match
targets, actions, and phases. An install parses the downloaded file with the
schema compiled into its binary and refuses the whole document when it meets
something it does not know:

- an unknown key anywhere — `deny_unknown_fields` is set on every spec struct —
  for example a match or category field added after that binary was built;
- an unknown `in` target, action, or phase value;
- a construct whose semantics that build does not implement.

The refusal is total on purpose. Evaluation order is part of the contract, so a
half-understood candidate is more dangerous than an unreadable one: a skipped
rule could silently drop a BLOCK.

### What happens instead of a partial apply

`src/rules_update.rs` downloads the candidate, verifies its SHA256 digest, and
compiles it **together with the local configuration** (`overrides_file`, inline
categories, size limits, regex compilation, ReDoS guards) before touching
anything on disk. Only a candidate that passes everything replaces the file, by
atomic rename; the state sidecar (`rules.yaml.update-state`) is written the same
way. Any failure — network, checksum, UTF-8, size, validation — leaves the
previous file exactly as it was.

The daemon keeps evaluating the last known good rules, logs the failure, and
retries after `min(interval, 10 minutes)` (so the default 24h interval retries
every 10 minutes until the file changes). A broken publication therefore cannot
take an install down or weaken it. The cost is quieter: the install keeps
working, but its rules stop moving — new CVE signatures never arrive, and the
traffic itself looks normal. That silent freeze is what the guards below prevent
and detect.

## The contract

- The published set stays readable by the **newest release**. Nothing older is
  guaranteed.
- Adding a field, match target, action, or phase to the engine is a **release
  event**, not a rule-update event: rules may use it only after a release that
  understands it.
- An install that wants rules published for a newer format upgrades its binary
  (rerun the installer). Until then it keeps protecting with its current rules,
  and the refused updates are counted.

Older installs are deliberately out of scope. Supporting several releases at once
would mean publishing one channel per format (for example `dist/v1/rules.yaml`),
which needs a subsetting generator and a second baseline to maintain forever. The
repository keeps one channel and expects installs to follow releases.

A version marker inside the rules file cannot express this contract: a binary
that predates the marker rejects unknown keys wholesale, so the marker itself
would be the construct it cannot read. The release tag is the only place a build
can be told which format to expect — which is why the baseline is derived from
the tags rather than declared in the file.

## Guard 1: the compatibility gate

`scripts/check-rules-compat.sh` is the ground truth: it validates the published
file with the actual released binary.

1. The baseline is the newest `v*` tag (`git describe --tags --abbrev=0 --match
   'v*'`), or `KUNATO_RULES_BASELINE=<tag>`.
2. Unless `KUNATO_RULES_BIN=<binary>` points at one, the tag's tree is extracted
   with `git archive` into `target/rules-compat/<tag>` and built there with the
   tag's own lockfile (`cargo build --release --locked`).
3. The baseline binary runs `--validate` on a minimal configuration whose
   `rules_file` points at `dist/rules.yaml`, and the construct it cannot read is
   printed on failure.

The first run builds the baseline (about two minutes); later runs reuse the
binary. It runs in two places, so an incompatible publication cannot reach
`main`:

| Workflow | Where | Effect |
| --- | --- | --- |
| `.github/workflows/ci.yml` | last step, on every push | the push that introduced the construct goes red |
| `.github/workflows/daily-cve.yml` | after `scripts/update-dist-rules.sh`, before the commit | the daily job commits nothing while the published set is unreadable by the newest release |

The daily agent runs the same script inside its own loop
(`.github/prompts/daily-cve.md` and the coverage skill) and is instructed to
leave out a rule that would need a newer build, reporting the gap instead of
breaking publication.

### What the gate does not cover

- Only `dist/rules.yaml` is gated. Constructs a user writes in their own
  configuration or `overrides_file` are validated by the binary that loads them,
  which is the right authority for local edits.
- The baseline is the newest tag only. An install pinned to a release asset is
  self-consistent by construction, so it needs no gate.
- On a repository without a `v*` tag the check prints a notice and passes, and
  building the baseline needs cargo and access to crates.io the first time.

## Guard 2: publication channels

`rules_update.url` decides how far the rules can drift from the binary:

| URL | Changes | Format guarantee |
| --- | --- | --- |
| `.../main/dist/rules.yaml` (installer default) | every day | newest release, enforced by the gate |
| `.../releases/latest/download/rules.yaml` | when a release is cut | the release's own snapshot, valid by construction |
| `.../releases/download/<tag>/rules.yaml` | never | frozen at that release |

Releases publish their rule set as assets, so an install can follow releases
instead of `main` and never meet a construct its binary does not know. The
rolling `main` channel is the default because it carries new signatures daily;
the gate makes it safe by keeping it inside the released format.

## What an operator sees

| Situation | Rule file on disk | Active rules | Logs and metrics |
| --- | --- | --- | --- |
| New compatible rules | replaced | new rules after hot reload | `kunato_rules_update_success_total` |
| No new version (`304`) | untouched | unchanged | `kunato_rules_update_not_modified_total`, `kunato_rules_last_success_timestamp_seconds` refreshed |
| Rules need a newer build | untouched | previous rules | `kunato_rules_update_incompatible_total` (and `..._failure_total`), log: "the published rule set needs a newer Kunato build" |
| Network, checksum, size, or invalid rules | untouched | previous rules | `kunato_rules_update_failure_total` |
| Local rules file edited into an invalid state | replaced by the editor | previous rules (reload refused) | `kunato_reload_failure_total` |

Alerting follows directly from the split:

- `increase(kunato_rules_update_incompatible_total[1h]) > 0` — an install is
  frozen and needs a binary upgrade; the counter grows on every retry.
- `time() - kunato_rules_last_success_timestamp_seconds > 48h` — rules have
  stopped moving for any reason.

Both are also visible without metrics: the refusal is an `ERROR` log line with
the offending field, repeated every ten minutes.

## Releasing a new rule construct

1. Add the field, target, action, or phase to the engine, its tests, and
   `README.md`. No published rule may use it yet; the gate stays green because
   the published set has not changed.
2. Bump `version` in `Cargo.toml` to the tag (for example `0.3.0` for
   `v0.3.0`) so `kunato --version` identifies the release; `release.yml` fails
   the build when the tag and the package version disagree. Then cut the
   release (`v*` tag). `release.yml` builds the binaries and publishes the rule
   set of that commit as a release asset; the gate's baseline becomes this tag,
   and the installer serves it to new installs.
3. From now on daily updates may use the construct: the gate validates against
   the new baseline, and a rule that uses it only fails the build if the release
   is missing.
4. Installs that want those rules rerun the installer. Until they do, they keep
   their previous rules; the strict schema means no rule is ever half-applied.

If a construct reaches `rules.example.yaml` before its release, the gate fails
the build on purpose: the fix is to cut the release (or to keep the rule out
until then), never to relax the gate.

### Worked example (2026-10-17)

The login brute-force throttle (`login-throttle`) was published using the
per-rule `limit` construct. The v0.1.0 release predates that field, so every
v0.1.0 install rejected the whole published set from that moment and kept the
rules it had — protection continued, coverage froze. Diagnosing it took three
steps that are now automated: the rejection named the offending key, the gate
reproduces it in seconds once the baseline is built, and the remedy was a
release: v0.2.0 moved the baseline to the current schema, CI and the daily job
went green, and installs resume updates after the installer rerun. The counter
`kunato_rules_update_incompatible_total` is what would have made the freeze
visible without reading logs.

## Where the pieces live

| Piece | Path |
| --- | --- |
| Published rule set and checksum | `dist/rules.yaml`, `dist/rules.yaml.sha256` |
| Generator (example → published set) | `scripts/update-dist-rules.sh` |
| Compatibility gate | `scripts/check-rules-compat.sh` |
| Workflow wiring | `.github/workflows/ci.yml`, `daily-cve.yml`, `release.yml` |
| Agent instructions | `.github/prompts/daily-cve.md`, `.agents/skills/kunato-cve-coverage/SKILL.md` |
| Updater (download, verify, swap, retry) | `src/rules_update.rs` |
| Schema and whole-file validation | `src/config/mod.rs` |
| Failure classification | `src/error.rs` (`unsupported_construct`, `RulesNeedNewerBuild`) |
| Metrics | `src/metrics.rs`, served on the admin listener |
| Publication guards for `dist/` | `src/config/mod.rs` unit tests (matches `rules.example.yaml`, checksum current) |
| Policy summary | `README.md`, "Rule set format compatibility" |
