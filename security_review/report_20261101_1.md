- **診断日:** 2026-11-01
- **対象リポジトリ:** Kunato (`v0.15.3` / `docs/improve-readme` ブランチ時点)
- **診断観点:**
  1. **観点1: Kunato 自身の脆弱性**（リソース枯渇・DoS、並行性・状態管理、TLS/ACME/ルール更新/アップグレード、ロギング・CLI・インストーラ権限管理）

## エグゼクティブサマリ

Kunato はメモリ安全な Rust で実装されており、入力サイズ制限・ReDoS ガード・アトミックな設定スワップなど堅牢な基本設計を備えています。一方で、全モジュールのコードパスおよびデータフローを精査した結果、以下の **計 27 件（観点1: 12件、観点2: 15件）** の脆弱性および防御上のバグ・ギャップが確認されました。

### [KUNATO-SELF-01] Critical: `InspectionBudget` の過剰予約・解放遅延とレスポンス送信タイムアウト欠如によるプロセス全体の検査メモリ予算枯渇 DoS

- **該当箇所:**
  - `src/proxy/server.rs:50-58` (`INSPECTION_BUDGET_BYTES`, `REQUEST_INSPECTION_FACTOR`, `RESPONSE_INSPECTION_FACTOR`)
  - `src/proxy/server.rs:197-260` (`ActivityBody`, `connection_is_idle`)
  - `src/proxy/server.rs:321-336` (`Context::reserve_response_inspection`)
  - `src/proxy/server.rs:728-788` (`serve_io`)
  - `src/proxy/server.rs:1542-1558`, `1845-1967` (`process`)
  - `src/proxy/response.rs:240-243` (`response::inspect`)

- **根本原因:**
  プロセス全体のボディ検査メモリ上限を管理する `InspectionBudget`（上限 `INSPECTION_BUDGET_BYTES = 256 MiB`）の予約・解放と、クライアントへのレスポンス送信制御に以下の3つの問題が重なっています。
  1. **`Content-Encoding` 存在時の無条件な最大予算（64 MiB）予約と未縮小 (`src/proxy/server.rs:1542-1558, 1849`):**
     ```rust
     let encoded = parts.headers.contains_key(CONTENT_ENCODING);
     let decode_body = inspect_body || ((inspect_uploads || inspect_form) && encoded);
     if (decode_body || inspect_uploads) && !body.is_empty() {
         let raw_bytes = if encoded {
             config.limits.max_body_bytes
         } else {
             body.len()
         };
         if !grow_inspection_to(&mut inspection, request_inspection_bytes(config, raw_bytes)) {
     ```
     リクエストに `Content-Encoding` ヘッダがありボディが 1 バイト以上ある場合、実際のボディ長やエンコーディング種別（展開処理すら行われない `Content-Encoding: identity` を含む）にかかわらず、`raw_bytes = config.limits.max_body_bytes`（既定 8 MiB）として **1リクエストあたり `8 MiB × 8 = 64 MiB`** が `InspectionBudget` から予約されます。さらにルール評価完了後に `drop(view)` したあとも予約量は実際の `payload.prefix.len()` に縮小されず、64 MiB を保持したまま上流応答待ち・レスポンス完了まで拘束されます。
  2. **レスポンス検査における一律 `3 MiB`（最大 `24 MiB`）予約と未縮小 (`src/proxy/server.rs:321-336`, `src/proxy/response.rs:240-243`):**
     `reserve_response_inspection` はレスポンスボディ長にかかわらず常に `max_response_body_bytes × 3`（既定 3 MiB）を一括予約し、レスポンスルール評価完了後も実際のバッファサイズへ縮小せず `buffered.body.with_guard(Arc::new(inspection))` としてレスポンスストリーム完了まで保持し続けます。
  3. **下流レスポンス送信タイムアウトの欠如と HTTP/2 アイドル監視の無効化 (`src/proxy/server.rs:197-260, 728-788`):**
     クライアントが TCP 受信ウィンドウや HTTP/2・HTTP/3 のストリームウィンドウを絞ってレスポンスボディの読み取りを止めると、`PrefixBody` に紐づく `InspectionGuard` が解放されません。HTTP/1.1 には書き込みタイムアウトがなく、HTTP/2 でも `ActivityBody` がストリーム終了まで `ActiveRequest` を保持するため `activity.active` が `0` にならず、`connection_is_idle` ウォッチドッグが発火しません。

- **影響:**
  `Content-Encoding` 付きの小サイズリクエストがわずか 4 並列で処理中になるか、単一の HTTP/2 接続上で約 85 ストリームのレスポンス読み取りを滞留させるだけで、プロセス全体の `InspectionBudget` (256 MiB) が 100% 枯渇し、他のすべてのクライアントのリクエストが `503 Service Unavailable ("inspection capacity exhausted")` で拒否されます。

- **推奨される修正方針:**
  1. `InspectionGuard` に `shrink_to(&mut self, bytes: usize)` メソッドを追加し、リクエストルール評価直後およびレスポンスルール評価直後に、実際に保持し続けるバッファ長まで予約量を即座に縮小する。
  2. リクエスト展開およびレスポンスバッファリング時も最大値を一括予約するのではなく、実際に読み取った／展開したバイト数に応じて段階的に `grow` し、`Content-Encoding: identity` では展開用の追加予約を行わない。
  3. 下流クライアントへのレスポンスボディ送信にもデッドライン（または進捗がないストリームを打ち切る書き込みアイドルタイムアウト）を設ける。

### [KUNATO-SELF-02] High: `ProtectionState` におけるグローバル `tracked_ips` カウンタとシャードローカル退避 (`evict_oldest`) の不整合によるシャード飢餓 (503 DoS) および全シャードロック走査

- **該当箇所:**
  - `src/protection/mod.rs:516-552` (`client_shard`)
  - `src/protection/mod.rs:639-708` (`check_rule_limit`)
  - `src/protection/mod.rs:1055-1100` (`shard_index`, `evict_stale`, `evict_oldest`, `reserve_slot`)

- **根本原因:**
  1. **グローバル上限とシャードローカル退避の不整合 (`src/protection/mod.rs:516-552`):**
     `ProtectionState` は 16 シャード（`SHARD_COUNT = 16`）に IP エントリを分散していますが、上限 `max_tracked_ips`（既定 100,000）は全シャード共通の単一 `AtomicUsize` (`self.tracked_ips`) で管理されています。
     `shard_index` は決定論的（IPv4 では最終オクテットの下位 4 ビット）であるため、特定の 1 シャードにマップされる IP 群だけで `tracked_ips` の 100,000 枠すべてを埋めることができます。
     この状態で他のシャード（例: 空になったシャード 0、または全エントリがアクティブ接続中／BAN 中のシャード）に新規 IP が到着すると、`evict_stale` でも枠が空かず、`evict_oldest(&mut shard.entries, now)` は**自シャード内からしか退避候補を探さない**ため `false` を返し、`client_shard` が `None` を返します。
  2. **満杯到達後の毎リクエスト全 16 シャードロック＋10万件線形走査 (`src/protection/mod.rs:526-548, 655-683`):**
     `evict_oldest` は 1 件削除して 1 件挿入するため `tracked_ips` は `max_tracked_ips` のまま減少しません。その結果、一度上限に達すると以降 600 秒間（`STALE_AFTER`）、未登録 IP からリクエストが来るたびに毎回全 16 シャードの Mutex を順次ロックして 100,000 件の `retain` (`evict_stale`) と線形探索 (`min_by_key`) が実行されます。また `check_rule_limit` には `evict_oldest` すら存在しません。
  3. **退避による違反回数・BAN バックオフ・行動検知状態のリセット:**
     `evict_oldest` は `connections == 0` の非 BAN エントリを削除するため、特に `trusted_proxies` 環境（解決後クライアント IP の `connections` が常に `0`）では、エントリ退避を起こすことで `violations`、`ban_count`、`BehaviorEntry` を初期状態にリセットできます。

- **影響:**
  1 シャード分の IP 群でテーブルを埋めるだけで、残り 15 シャード（全 IP 空間の 93.75%）に属する新規クライアントが 10 分間にわたり `503 Service Unavailable` で拒否されます。さらに毎リクエスト全シャードロックと 10 万件走査が走り、深刻な CPU 枯渇を引き起こします。

- **推奨される修正方針:**
  1. グローバルな `tracked_ips` / `tracked_rules` カウンタを廃止し、各シャードごとに独立した上限 `per_shard_limit = (config.max_tracked_ips / SHARD_COUNT).max(1)` を設ける。
  2. `evict_stale` の実行にシャード単位のクールダウン（例: 数秒〜30秒に1回）を設け、最古エントリの退避も $O(1)$ の LRU 構造で管理する。

### [KUNATO-SELF-03] High: HTTP/3 (QUIC) リスナーにおける送信元検証前の `ConnectionGuard` 確保とハンドシェイク・ヘッダ読み取りタイムアウト欠如による接続枠枯渇 DoS

- **該当箇所:**
  - `src/proxy/http3.rs:97-125` (`serve`)
  - `src/proxy/http3.rs:137-220` (`serve_connection`, `serve_h3`, `handle_request`)

- **根本原因:**
  1. `http3::serve` (`src/proxy/http3.rs:100`) は、`endpoint.accept()` が返した未検証の UDP パケット送信元 `incoming.remote_address()` に対して、QUIC ハンドシェイクや Retry 検証を行う前に `context.try_acquire_connection(peer.ip())` を呼び出し、TCP と共有される `global_connections`（既定 1024）および IP 別 `connections`（既定 32）を確保します。
  2. TCP リスナーと異なり、`connecting.await`（151行目）、`builder.build(...).await`（171行目）、`resolver.resolve_request().await`（214行目）のいずれにも `timeouts.header_read`（既定 10 秒）が適用されておらず、`timeouts.connection_idle`（既定 60 秒）まで解放されません。

- **影響:**
  送信元 IP を偽装した QUIC Initial UDP パケットによって、最大 60 秒間サーバ全体の `max_connections`（TCP の HTTP/1.1・HTTP/2 を含む）または特定の正規ユーザ IP の `max_connections_per_ip` を枯渇させ、全通信を `503` にできます。

- **推奨される修正方針:**
  1. `connecting.await`、`builder.build(...).await`、`resolver.resolve_request().await` に `config.timeouts.header_read` のタイムアウトを適用する。
  2. TCP と共有される `ConnectionGuard` の確保は QUIC ハンドシェイク完了後（送信元 IP の到達性が証明された後）に行うか、未検証のハンドシェイク中 QUIC 接続には独立した上限とアドレス検証（`incoming.retry()`）を導入する。

### [KUNATO-SELF-04] High: WebSocket トンネルにおけるレート制限・検査コスト課金の欠落およびフレームヘッダ宣言長による先行メモリ確保・検査予算占有

- **該当箇所:**
  - `src/proxy/websocket.rs:432-537` (`pump_client_to_upstream`)
  - `src/proxy/websocket.rs:628-661` (`MessageBudget`)
  - `src/proxy/websocket.rs:663-751` (`read_frame`)

- **根本原因:**
  1. `pump_client_to_upstream` (`src/proxy/websocket.rs:498-508`) はメッセージごとに WAF ルール評価を行いますが、`ProtectionState::check_request`・`check_global`・`charge_inspection` を一切呼び出していません。
  2. `read_frame` (`src/proxy/websocket.rs:716-738`) は、2〜10 バイトのフレームヘッダで宣言された `len`（最大 `websocket_message_bytes`、既定 1 MiB / 最大 8 MiB）のみに基づいて、ペイロードを受信する前に `budget.ensure(len as usize)` で `len * 2` の `InspectionBudget` を予約し、`vec![0u8; len as usize]` を一括確保してから `read_exact` に入ります。またフラグメント蓄積時も残り許容サイズではなく `message_limit` 全体が `read_frame` に渡されます。

- **影響:**
  確立済みの WebSocket 接続上でレート制限や自動 BAN を一切受けずに大量のメッセージを送り続けて CPU を消費させることや、大きなフレーム長を宣言したヘッダのみを送ってペイロード送信を遅延させることでプロセス全体の `InspectionBudget` (256 MiB) とメモリを占有することができます。

- **推奨される修正方針:**
  1. WebSocket メッセージ検査時にも `protection.check_request` および `protection.charge_inspection` を適用し、制限超過時はトンネルをクローズする。
  2. `read_frame` には残りメッセージ許容長 `message_limit.saturating_sub(message.payload.len())` を渡し、固定サイズチャンクで読み進めながら段階的にバッファと `MessageBudget` を拡張する。またフレーム／メッセージ読み取りにタイムアウトを設ける。

### [KUNATO-SELF-05] Medium: インツリー YAML パーサ (`FlowCursor::location_at`) における単一行フローコレクションの $O(N^2)$ 時間計算量

- **該当箇所:**
  - `src/yaml/parser.rs:280-300` (`FlowCursor::location_at`, `line`, `column`)
  - `src/yaml/parser.rs:1066-1067, 1114-1115, 1150-1151, 1242-1243, 1306-1307`

- **根本原因:**
  `FlowCursor::location_at` は呼び出されるたびに `self.text[line.offset..pos].chars().count()` を計算します。単一行に多数の要素を持つフローコレクション（`[a, b, c, ...]` や `{k: v, ...}`）では `line.offset` が常に `0` となるため、要素ごとに毎回行頭から現在位置までの文字数カウントが走り、要素数 $N$ に対して $O(N^2)$ の計算量となります。

- **影響:**
  `rules_update` や設定リロードで単一行フロー形式の大きな YAML が与えられた際、非同期ワーカースレッドが長時間ブロックします。

- **推奨される修正方針:**
  `FlowCursor` に現在の `(line, column)` をフィールドとして持たせ、`bump()` 時に $O(1)$ でインクリメンタルに更新する。

### [KUNATO-SELF-06] Medium: `rules_update` のタイマー境界バグ・状態保存失敗時の無限スピンループ、およびホットリロードの非同期スレッド阻害・3重実行・競合

- **該当箇所:**
  - `src/rules_update.rs:67-128`, `207-240`, `516-556`, `614-623`
  - `src/config/watcher.rs:58-85`, `99-172`
  - `src/main.rs:234-250`

- **根本原因:**
  1. `delay_until_due` (`src/rules_update.rs:617`) の `Duration::from_secs(next_due).checked_sub(now)` は `next_due == now` の秒の間 `Some(Duration::ZERO)` を返すため、Unix 秒が次の 1 秒に進むまで `sleep(Duration::ZERO)` とファイル読み取りを繰り返すビジーループが発生します。
  2. `rules_update::run` は更新成功時に `if succeeded { continue; }` でスリープせずループ先頭へ戻り、`state_file` に書き込まれた `next_due` を読んでスリープします。しかし `write_state` (`src/rules_update.rs:552-556`) は書き込み失敗を `warn!` のみで無視するため、`state_file` の書き込み・読み取りが失敗している環境では `delay_until_due` が常に `None` を返し、**待機時間ゼロでリモートサーバへ無限に HTTPS リクエストを送信し続けるループ**になります。
  3. `update_once`・`rules_update::run` の `watcher::reload`・`spawn_sighup_reload` は Tokio の非同期ワーカースレッド上で直接同期ファイル I/O と正規表現コンパイルを実行しており、かつルール更新 1 回につき最大 3 回（`update_once`、`rules_update::run`、`watcher::watch`）コンパイルが走り、同時リロード時の排他制御もありません。また `write_atomic` (`src/rules_update.rs:524`) の一時ファイル名が予測可能な `.{file_name}.{pid}.tmp` になっています。

- **影響:**
  状態ファイル更新失敗時の無限リクエストループ、およびルール更新時のワーカースレッドストールや古い設定スナップショットによる競合上書きが発生し得ます。

- **推奨される修正方針:**
  1. `delay_until_due` で `delay.is_zero()` を `None` とし、かつメモリ上でも次回のスリープ期間を保持して `write_state` 失敗時にも必ず `interval` 分スリープさせる。
  2. リロード処理を単一の排他ロック／チャネルで直列化して `spawn_blocking` で実行し、`update_once` でコンパイル済みの `CompiledConfig` を再利用する。
  3. `write_atomic` に乱数サフィックスと `OpenOptions::create_new(true)` を使用する。

### [KUNATO-ORIGIN-01] High: `path_forms` が最終デコード結果のみを正規化することによる `ALLOW` ルール・`content_routes`・パスルールのバイパス

- **該当箇所:**
  - `src/request_view.rs:81-92` (`path_forms`)
  - `src/config/mod.rs:1634-1641` (`ContentRoute::matches`), `3234-3240` (`compile_matcher`)
  - `src/proxy/server.rs:1508-1517` (`graphql_path`)

- **根本原因:**
  `RequestView` のパス候補を生成する `path_forms` (`src/request_view.rs:81-92`) は、最大2回のパーセントデコードを行った後、**最後の要素（`forms.last()`、すなわち2回デコード後の文字列）に対してのみ** `normalize_path` を呼び出しています。
  ```rust
  pub(crate) fn path_forms(path: &str) -> Vec<Cow<'_, str>> {
      let mut forms = percent_decode_forms(path);
      let last = forms.last().map(|form| form.as_ref()).unwrap_or(path);
      if let Some(normalized) = normalize_path(last)
          && !forms
              .iter()
              .any(|form| form.as_ref() == normalized.as_str())
      {
          forms.push(Cow::Owned(normalized));
      }
      forms
  }
  ```
  （対照的に、`src/php.rs:29-32` では `percent_decode_forms` の各段階すべてに `normalize_path` を適用しています。）
  パス内に二重エンコードされたスラッシュ `%252f` とドットセグメント `..` が混在している場合（例: `/allowed/a%252fb/../../secret`）：
  - 未デコード（Form 0）および1回デコード後（Form 1: `/allowed/a%2fb/../../secret`）では、`a%2fb` は**1つのセグメント**であるため、2つの `..` を解決する一般的なオリジン（RFC 3986 に従い `%2f` をパス区切りとみなさない、または1回のみデコードするオリジン）では **`/secret`** にルーティングされます。
  - しかし Kunato は Form 2（2回デコード後: `/allowed/a/b/../../secret`）に対してのみ `normalize_path` を呼ぶため、正規化結果は **`/allowed/secret`** となり、`view.path_forms` の全要素が `/allowed/` で始まる状態になります。

- **影響:**
  `ALLOW` ルールや `content_routes` は「`path_forms` の全要素が一致すること（`.all()`）」を検証していますが、生成される `path_forms` 自体に1回デコード後の正規化パス（`/secret`）が欠落しているため、プレフィックス一致の `ALLOW` ルールや `content_routes`（ボディ検査免除）をバイパスして任意のエンドポイント `/secret` に到達できます。

  プロキシ転送時に Trailer フレームを破棄（ストリップ）するか、またはヘッダサイズ上限とヘッダルール評価を適用する。

### [KUNATO-ORIGIN-14] Medium: 文字コード（Charset: UTF-16 / UTF-7 / IBM037 / Shift_JIS 等）変換および XML UTF-16 BOM の未サポート

- **該当箇所:**
  - `src/decoding.rs:128-178`
  - `docs/attack-coverage.md:304-324`

- **根本原因:**
  Kunato はすべてのボディを UTF-8 / ASCII として `String::from_utf8_lossy` で変換して検査しますが、`Content-Type` に `charset=utf-16`, `charset=utf-7`, `charset=ibm037`, `charset=shift_jis` 等が指定された場合や XML が UTF-16 BOM (`FE FF` / `FF FE`) で始まる場合に、文字コード変換も `415 Unsupported Media Type` による拒否も行いません。

- **推奨される修正方針:**
  非互換な `charset` パラメータや UTF-16 / UTF-32 BOM を持つリクエストを `415 Unsupported Media Type` で拒否するか、UTF-8 へのトランスコード層を追加する。併せて `docs/attack-coverage.md` にカバレッジ状況を明記する。

### [KUNATO-ORIGIN-15] Medium: 同梱ルール（`rules.example.yaml`）および行動検知パス判定における具体的なバイパス

- **該当箇所:**
  - `rules.example.yaml:73-96`, `555`, `1032-1034`, `1148-1155`, `1262-1268`, `1527-1528`
  - `src/protection/mod.rs:965-974` (`auth_path_matches`)

- **根本原因と修正案:**
  1. **SQL Injection (`union-select`, 1032行目 & `lansweeper-sqli`, 555行目 & `boolean-taunts`, 1034行目):**
     - `union-select` が `UNION` と `SELECT` の間の括弧 `(` を許容しておらず、`lansweeper-sqli` は `\(select\b` で `(` の直後の空白を許容していないため、`UNION( SELECT ...)` が両方をすり抜けます。また `boolean-taunts` は `OR` の直後に空白・`+` を要求しており `OR/**/1=1` や `OR(1)=1` にマッチしません。
     - **修正:** セパレータに括弧 `(` とコメント `/*...*/` を許容する。
  2. **Parameter Pollution (`parameter-pollution`, 73-96行目):**
     - クエリ/フォーム用正規表現の中間グループ `(?:[^&\s]{0,256}&)?` が最大1回しか繰り返されないため、間に2個以上の無関係なパラメータが挟まるとマッチしません。JSON 用正規表現も `[^}]{0,256}` のため、間に空オブジェクト `{}` が1つあるだけで止まります。
     - **修正:** クエリ/フォームの中間グループを `(?:[^&\s]{0,128}&){0,16}` 等に拡張し、JSON 重複キーは `limits.hardening.duplicate_json_keys` の利用を推奨または有効化する。
  3. **XSS (`xss.event-handlers`, 1150行目):**
     - SVG の `onbegin`, `onend`, `onrepeat`、CSS 連動の `oncontentvisibilityautostatechange`、`autofocus` 連動の `onfocusin`, `onfocusout`、`onbeforetoggle`, `onpageshow` 等の自動発火イベントハンドラがリストに含まれていません。
     - **修正:** 上記イベントハンドラ名を `xss.event-handlers` に追加する。
  4. **SSRF (`ssrf.internal-addresses`, 1262行目 & `single-label-host`, 1268行目):**
     - `://` の直後に userinfo `(?:[^/?#@\s]+@)?` があるケースや、ホスト名末尾に DNS ルートドット `.` が付くケース（`http://localhost./` 等）にマッチしません。
     - **修正:** optional な userinfo と末尾ドット `\.?` を正規表現に追加する。
  5. **JWT `none` アルゴリズム (`jwt.none-algorithm`, 1527行目):**
     - Base64 プレフィックス固定列挙のため、先頭空白 `{ "alg":"none"}` や小文字 `"typ":"jwt"` でバイパスされます。
     - **修正:** デコード検査を行う `limits.jwt` の有効化を推奨するか、Base64 パターンを拡張する。
  6. **行動検知の認証パス判定 (`src/protection/mod.rs:965-974`):**
     - `auth_path_matches` がマトリックスパラメータ（`;jsessionid=...`）を除去せずに末尾 `$` アンカー付き正規表現と照合するため、`/login;jsessionid=xxx` へのブルートフォースが認証失敗としてカウントされません。
     - **修正:** `auth_path_matches` でも `;` 以降を除去したパスフォームを照合対象に含める。
