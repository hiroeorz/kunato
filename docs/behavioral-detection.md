# Behavioral bot and authentication-abuse detection

Status: Phase 1 and the opt-in `behavior.scraping` / `global_auth.action: BLOCK`
parts of Phase 3 are implemented; challenges, configurable static exclusions, and
the remaining Phase 2/3 items are future work.

Related documents:

- `docs/DESIGN.md`, Section 7 (DoS / DDoS protection)
- `docs/attack-coverage.md` (Bot, enumeration, and credential-abuse rows)
- `docs/development.md`, "DoS / DDoS Protection"

## Summary

- Observe upstream response statuses after forwarding and keep a per-source,
  tumbling behavior window.
- Flag a source for **enumeration** when it produces many `404`s on many
  distinct non-static paths.
- Flag a source for **authentication abuse** when it produces many `401`/`403`
  responses on login/token/session/MFA/SSO paths.
- Flag **distributed authentication abuse** when the global failure count over
  a window crosses a threshold, even though each source stays below its
  per-source threshold.
- Default to `LOG`; allow `BLOCK` per signal. A `BLOCK` flag bans the source for
  subsequent requests and reuses the existing ban escalation.
- Keep the state fixed-size inside the existing tracked-source table, with no
  new dependencies and no network calls.

## 1. Context

Kunato already combines three layers for abusive traffic:

1. protocol and resource limits (header/body timeouts, connection caps, body
   inspection limits),
2. per-source and global rate limits plus bans (`protection`),
3. YAML signatures (`scanners-and-bots`, `login-throttle`, CVE categories).

The remaining gaps in `docs/attack-coverage.md` are not missing request
signatures. They are classes in which a single request is indistinguishable
from legitimate traffic:

- an iterative prober that requests many nonexistent paths slowly,
- a login brute-force or spray that stays below each per-source budget,
- a credential-stuffing campaign spread across many source addresses,
- a scanner whose User-Agent is not in the signature list.

The common missing capability is a stateful view of *outcomes*. This design adds
a bounded, per-source behavior window that observes upstream response statuses,
plus a global authentication-failure window for distributed attempts. It sits
next to the existing rate limiter and ban manager and does not consult or depend
on the YAML rule set.

## 2. Goals and non-goals

### Goals

- Detect source-local **enumeration/probing**: many `404` responses, especially
  on many distinct paths, within a short window.
- Detect source-local **authentication abuse**: repeated `401`/`403` responses
  on authentication paths.
- Detect **distributed authentication abuse**: a high aggregate number of
  authentication failures across many sources.
- Make the first release **observation-first**: metrics and sampled logs, with
  blocking opt-in. This avoids shipping a heuristic that can break legitimate
  traffic before it has been tuned.
- Reuse existing per-source tracking, IPv6 aggregation, allowlists, ban
  escalation, and the bounded tracking table.
- Keep the deployment surface unchanged: one binary, one YAML file, no external
  services or new dependencies.

### Non-goals

- JavaScript challenges, CAPTCHAs, or proof-of-work.
- Per-user, per-session, or cookie-based tracking. The source key is the same
  IP / IPv6-prefix key used by rate limits and bans.
- Content classification (spam, comment quality) or business-logic abuse such as
  coupon abuse, inventory hoarding, or mass assignment.
- Detecting a slow scraper below the configured `behavior.scraping` thresholds
  or one spread across many source addresses.
- Blocking the response that triggered a flag. Detection runs after the upstream
  response; a `BLOCK` action bans the source for subsequent requests.
- A global deny-all or global ban. `global_auth.action` defaults to `LOG`; an
  opt-in `BLOCK` action can deny authentication to legitimate users during an
  attack and must be tuned and allowlisted before use.
- Persisting behavior state across restarts. State is in-memory and resets on
  restart, like the existing rate-limit state.

## 3. Requirements

### Functional

- **F1 — Observe upstream outcomes.** For every request that receives an
  upstream response, record the source, path, and response status. Do not
  observe responses generated by Kunato itself (rule blocks, host rejection,
  rate limiting, timeouts, upstream connect errors) or `101 Switching Protocols`.
- **F2 — Per-source enumeration signal.** Count `404` responses on non-static
  paths and approximate the number of distinct `404` paths in a window. Flag the
  source when the configured volume, ratio, and distinct-path thresholds are all
  met.
- **F3 — Per-source authentication signal.** Count `401`/`403` responses whose
  path matches an authentication-path pattern. Flag the source when the
  configured failure count is met.
- **F4 — Global authentication signal.** Sum authentication failures across all
  sources over a global window and flag once when the configured threshold is
  met. This is the only signal that can catch distributed spraying where each
  source remains under F3.
- **F5 — Actions.** The per-source signals support `LOG` (default) and `BLOCK`.
  `BLOCK` applies a ban to the source; the current response is still forwarded.
  The global signal is log-and-metric only in this release.
- **F6 — Exemptions.** `protection.enabled: false`, `--disable-protection`, and
  sources in `protection.allowlist` skip all behavior observation. Static asset
  paths are excluded from the enumeration numerator.
- **F7 — Transports.** HTTP/1.1, HTTP/2, and HTTP/3 use the same observation
  point. Non-`101` WebSocket handshake responses use it too.
- **F8 — Configuration.** The feature is configured under `protection.behavior`;
  an absent block uses conservative defaults (enabled, per-signal `LOG`).
- **F9 — Hot reload.** A new configuration is parsed and validated before it
  replaces the active one. Invalid behavior configuration keeps the previous
  configuration, like every other validation error.
- **F10 — Observability.** Add Prometheus counters and one log line per flag per
  window. Metrics distinguish observed failures from flags and applied bans.

### Non-functional

- **N1 — Bounded memory.** The behavior state adds a fixed number of bytes per
  tracked source and is bounded by `protection.max_tracked_ips`. It never stores
  raw paths, request bodies, or a per-path map.
- **N2 — Bounded CPU.** Observation is O(path length) for a hash plus O(1)
  counter updates. Authentication-path regexes are evaluated only for `401`/`403`
  responses, not for every request.
- **N3 — No new dependencies.** Use the existing `regex` crate, standard
  library, and existing `http` types.
- **N4 — No panics in request paths.** No `unwrap()`/`expect()` in request
  handling. A missing or evicted entry is a no-op, not an error.
- **N5 — No blocking work.** Do not hold a shard mutex across an `await`. Do not
  do I/O or logging while holding the mutex.
- **N6 — Fail open.** If behavior state cannot be recorded (entry missing,
  tracking table full), the request proceeds. Behavior detection must never turn
  memory pressure into a new denial of service.
- **N7 — Determinism.** Window rollover, ratio thresholds, and ban escalation
  are testable with `tokio::time::pause`/`advance` and synthetic IPs.
- **N8 — Independence.** The feature runs without any categories or rules. It is
  disabled by `protection.enabled: false`; it is not affected by rule reloads
  or rule validation.
- **N9 — Privacy.** Only path hashes and counters are retained. Paths and
  statuses are not exported or written to disk beyond the log line for a flag.

## 4. Signal model

### 4.1 Observation point

The observation runs in `src/proxy/server.rs` after `forward::forward_request`
returns a response and before response-phase rules run. The HTTP/3 path reaches
the same `process` function through `process_payload`, so one hook covers all
three transports. In the WebSocket branch, observe the non-`101` response
returned by `websocket::forward_handshake`; a `101` handshake is not an
authentication or enumeration outcome.

Responses created by Kunato (admission rejection, host policy, rule `BLOCK`,
GraphQL rejection, upload rejection, `502`, `504`, inspection overload) are
produced before or instead of `forward_request` and are therefore not observed.
If the source is already banned (by a behavior flag or by the rate limiter), the
response is not observed either, so in-flight requests cannot escalate a ban.

Observation does not wait for the response body. It uses the status line only,
so streaming responses keep their current behavior.

Exemption follows the same boundary as rate limits: only
`protection.allowlist` (and `protection.enabled: false` or
`--disable-protection`) skips observation. An `ALLOW` rule, including the
bundled `trusted-sources` category, does not exempt a source from behavior
observation.

### 4.2 Definitions

Let a window be a fixed, tumbling interval (`behavior.window`, default 60 s).
Counters reset when the window expires; there is no sliding two-bucket window in
this release.

**Observed requests (`requests`).** Every response observed under F1, except
`101`. This is the denominator for the enumeration ratio. Static assets are
included in the denominator so that normal page loads dilute the ratio, while
their `404`s are excluded from the numerator.

**Enumeration (`not_found`).** A response with `404` whose path is not a static
asset (Section 4.4).

**Distinct enumeration paths (`distinct_404`).** Approximate cardinality of the
set of normalized `404` paths in the window, computed from a 256-bit Bloom
filter (Section 5.2). Query strings are not part of the hash; `?id=1` and
`?id=2` count as the same path.

**Authentication failure (`auth_failures`).** A response with `401` or `403`
whose path matches an authentication-path pattern (Section 4.5). This is counted
per source and also added to the global window.

**Global authentication failures (`global_auth_failures`).** The sum of
authentication failures across all sources in `global_auth.window`. With
`global_auth.action: BLOCK`, crossing the threshold rejects subsequent requests
on the authentication paths for `global_auth.ban`, regardless of source.

### 4.3 Trigger conditions

Enumeration flags when all of the following hold:

```text
requests        >= behavior.min_requests
not_found       / requests >= behavior.enumeration.not_found_ratio
distinct_404    >= behavior.enumeration.distinct_paths
```

Authentication flags when:

```text
auth_failures   >= behavior.auth.min_failures
```

Global authentication flags when:

```text
global_auth_failures >= behavior.global_auth.min_failures
```

Defaults are deliberately conservative:

| Setting | Default | Rationale |
| --- | --- | --- |
| `behavior.enabled` | `true` | Observation-only by default; no traffic change |
| `enumeration.action`, `auth.action` | `LOG` | Blocking is opt-in until thresholds are tuned |
| `behavior.window` | `60s` | Short enough to catch bursts, long enough to avoid noise |
| `behavior.min_requests` | `30` | Avoids judging low-volume clients |
| `enumeration.not_found_ratio` | `0.5` | The distinct-path threshold is primary; the ratio rejects normal browsing without being trivially diluted |
| `enumeration.distinct_paths` | `40` | A burst of distinct missing paths is scanner-like |
| `auth.min_failures` | `20` | Above the bundled login throttle's 10/60 s |
| `global_auth.window` | `60s` | Matches the source window |
| `global_auth.min_failures` | `100` | Distributed attempts only |
| `global_auth.action` | `LOG` | Blocking is opt-in after tuning |
| `global_auth.ban` | `60s` | Duration of the global auth-path block when action is `BLOCK` |

A slow prober that stays below every threshold is not detected. That is an
accepted limitation; rate limits and the rule set remain the outer controls.

### 4.4 Static asset exclusions

The enumeration numerator ignores paths that are normally fetched by page
loads. The check is a small, fixed helper (`is_static_asset`) rather than a
configurable list in this release:

- path prefixes: `/static/`, `/assets/`, `/build/`, `/dist/`, `/_next/static/`,
  `/images/`, `/img/`, `/fonts/`, `/media/`;
- exact paths: `/favicon.ico`, `/robots.txt`, `/sitemap.xml`,
  `/sitemap.xml.gz`, `/manifest.json`, `/site.webmanifest`;
- extensions (case-insensitive): `css`, `js`, `mjs`, `map`, `png`, `jpg`,
  `jpeg`, `gif`, `webp`, `avif`, `svg`, `ico`, `woff`, `woff2`, `ttf`, `otf`,
  `eot`, `mp4`, `webm`, `mp3`, `wav`, `ogg`, `flac`, `m4a`.

A `404` for `/.env`, `/.git/config`, `/admin`, or `/api/v1/users` is not a
static asset and counts. The helper receives the normalized path, so
`/assets/../.env` is treated as `/.env` and counts rather than being excluded by
the asset prefix. A user who browses a page with a missing image or a stale
source map receives `404`s but they are excluded from the numerator. The list
can become configurable later if operators need to add application-specific
asset prefixes.

### 4.5 Authentication paths

Authentication failures are counted only on paths that look like login, token,
session, MFA, or SSO endpoints. The default is the union of the bundled
`login-throttle` paths and common API/SSO forms:

```text
(?i)^/(wp-login\.php|xmlrpc\.php|login|logon|signin|sign_in|sign-in|session)(\.(php|do|jsp|aspx|html))?/?$
(?i)^/(users/sign_in|admin/login|api(/v[0-9]+)?/(auth|login|token|session|oauth|mfa|otp)|oauth|saml|auth|realms|openid-connect)(/|$)
```

Each pattern is validated at configuration load time with the same pattern-size
and regex-size limits as rule patterns, and the validated list is then compiled
into a `RegexSet`. A `401` on `/api/v1/users` (an expired token on a
normal API call) therefore does not count; a `401` on `/api/v1/token` does.
Matching normalizes each candidate form (the raw path and up to two
percent-decoded forms) for dot segments and duplicate slashes, mirroring rule
path handling, so `/lo%67in` and `//login` are still counted. Operators can
replace the defaults with `behavior.auth.paths`. An explicit empty list means no
path matches, so both the per-source and the global authentication signals
observe nothing. To
disable only the per-source flag while keeping the global signal on the default
paths, set `behavior.auth.enabled: false` and omit `behavior.auth.paths`.

Authentication path matching runs when either `auth.enabled` or
`global_auth.enabled` is true. The per-source counter and flag are updated only
when `auth.enabled` is true; the global window is updated whenever
`global_auth.enabled` is true. The detector does not read the `login-throttle`
rule from the rule set: it keeps its own compiled list so protection remains
independent of user rules. When the bundled login paths change, update the
default list in both places.

### 4.6 Debounce and window rollover

A signal sets a one-bit flag per source and window (`enumeration` or `auth`).
The log line and the flag metric are emitted only on the transition, not on
every subsequent response. When the window expires, the counters, bitmap, and
flags reset.

For `BLOCK`, the flag applies a ban and then resets the behavior window. This
ensures the source is not re-banned repeatedly within the same window and that
the next window starts after the ban, so a resumed attack is evaluated from
zero. The current response is forwarded unchanged; the next request is rejected
by the existing ban check with `429` and `Retry-After`.

The global window has a single `logged` bit; it emits at most one log line and
one flag metric per global window.

## 5. State model

### 5.1 Per-source state

`protection::Entry` gains a `BehaviorEntry`:

```rust
struct BehaviorEntry {
    window_start: Instant,       // 16 bytes on the supported platforms
    requests: u32,               // denominator for the enumeration ratio
    not_found: u32,              // 404s on non-static paths
    auth_failures: u32,          // 401/403 on authentication paths
    not_found_paths: [u64; 4],   // 256-bit Bloom filter of 404 paths
    flags: u8,                   // bit 0: enumeration, bit 1: auth
}
```

The inline state adds about 72 bytes per tracked source (including alignment),
so the default `max_tracked_ips: 100000` adds roughly 7 MB. This is comparable
to the existing per-source state and remains bounded. The struct is reset in
place on window rollover; no allocation occurs per response.

If `protection.max_tracked_ips` is exhausted, the existing admission path either
evicts a stale entry or rejects the connection; behavior observation does not
create entries. If the entry has been evicted between admission and response,
`observe_response` returns without recording and the request proceeds (N6).

### 5.2 Distinct path estimation

Use a 256-bit Bloom filter with two bit positions derived from a 64-bit FNV-1a
hash with a SplitMix64 finalizer (FNV-1a alone has weak low-bit diffusion for
short paths, which correlates the two positions):

```text
h = mix64(fnv1a64(normalized_path))
i1 = h & 0xff
i2 = (h >> 32) & 0xff
set bits i1 and i2 in not_found_paths
```

Let `X` be the number of set bits. Estimate cardinality with the standard Bloom
filter formula for `m = 256`, `k = 2`:

```text
n = -(m / k) * ln(1 - X / m)
```

If `X == m`, treat the estimate as 256 (the maximum representable threshold).
Collisions make the estimate conservative: it can under-count distinct paths,
so false positives are not created by collisions. The threshold is capped at
256 by validation.

Hash the normalized path when `crate::decoding::normalize_path` returns one, so
`/a//b`, `/a/./b`, and `/a/x/../b` count as the same path. Percent-decoding is
not applied here; encoded variants can inflate the count and only make detection
more sensitive.

### 5.3 Global state

`ProtectionState` gains a mutex-protected global window:

```rust
struct GlobalAuthWindow {
    started: Instant,
    failures: u32,
    logged: bool,
}
```

The mutex is taken only for `401`/`403` responses on authentication paths, not
for every request. At a few hundred authentication failures per minute this is
negligible. The window resets when `now - started >= global_auth.window`.

### 5.4 Concurrency

`observe_response` locks the same shard as admission (`shards[shard_index(key)]`)
and updates the entry in place. It does not call `client_shard` (which can evict)
and does not hold the lock while logging. The global lock is separate and is
taken after the shard lock is released to keep lock ordering simple. The global
window is updated even when the source entry is missing; only the per-source
update is skipped.

## 6. Configuration

Proposed YAML, nested under `protection`:

```yaml
protection:
  behavior:
    enabled: true
    window: 60s
    min_requests: 30
    enumeration:
      enabled: true
      action: LOG          # LOG (default) or BLOCK
      not_found_ratio: 0.5
      distinct_paths: 40
    auth:
      enabled: true
      action: LOG          # LOG (default) or BLOCK
      min_failures: 20
      # paths: []          # omit to use the built-in login/token/session list
    global_auth:
      enabled: true
      window: 60s
      min_failures: 100
```

Semantics:

- `behavior.enabled: false` disables all observation. `protection.enabled:
  false` and `--disable-protection` also disable it, regardless of this value.
- Each per-source signal has its own `action`, so enumeration can be raised to
  `BLOCK` while authentication abuse stays in `LOG` mode. The global signal is
  always `LOG` in this release.
- `enumeration.enabled` and `auth.enabled` allow turning off one source signal
  without disabling the whole feature.
- `auth.paths` is optional. When omitted, the built-in list is compiled. When
  provided, it replaces the built-in list; an empty list disables path matching
  for both source and global auth signals.
- `not_found_ratio` is compared as a floating-point ratio; a value of `0` means
  any `404` volume that also meets the distinct-path threshold qualifies.
- A `BLOCK` action reuses `protection.ban.duration` and `max_duration` for the
  ban and its escalation. It does not increment the rate-limit violation
  counter; a behavior flag is a direct ban trigger.

Validation rules:

| Field | Rule |
| --- | --- |
| `behavior.window`, `global_auth.window` | `> 0` and at most 1 hour |
| `behavior.min_requests`, `auth.min_failures`, `global_auth.min_failures` | at least 1 |
| `enumeration.not_found_ratio` | finite and between 0.0 and 1.0 |
| `enumeration.distinct_paths` | between 1 and 256 |
| `auth.paths` | at most 64 patterns, each at most 4096 bytes, each compiling under the configured regex size limits, and the combined set must build |
| `enumeration.action`, `auth.action` | `LOG` or `BLOCK`; unknown values are rejected by serde |

Configuration compilation follows the existing all-or-nothing model. Each
pattern is validated during `compile()` with the same pattern-size and
regex-size limits as rule patterns, then the validated list is compiled into a
`RegexSet`; an invalid pattern or a set that exceeds the regex construction
limit adds a validation issue and the reload keeps the previous configuration.
`Protection` stores the compiled `RegexSet`, not the raw strings, so request
handling never compiles a pattern and all auth patterns are checked in one pass.

The behavior block is a top-level configuration concern, not a rule field.
`rules.example.yaml` and `dist/rules.yaml` compatibility is unaffected: an older
release never sees this block in the managed rules file, and a rule-set update
does not change behavior.

Backward compatibility: a configuration without a `behavior` block uses the
defaults. A configuration that includes the block needs a build that understands
it, because `ProtectionSpec` denies unknown fields; an older binary rejects the
whole file rather than silently ignoring the block. There is no on-disk state
and no migration.

## 7. Runtime behavior

### 7.1 Observation flow

```text
admission (rate limit / ban)
  -> host policy
  -> body inspection and rule evaluation
  -> forward to upstream
  -> observe_response(peer.ip(), path, status, protection)
       -> update per-source counters, bitmap, and flags
       -> update global auth window when the status is 401/403 on an auth path
       -> optionally apply a ban when the signal action is BLOCK
  -> response-phase rules
  -> forward the response
```

The hook is placed immediately after `forward_request` returns and before the
`has_response_rules()` early return. The same function is called for non-`101`
WebSocket handshake responses. `process_payload` (HTTP/3) already delegates to
`process`, so no separate HTTP/3 hook is needed.

Pseudocode for the state update (locks shown explicitly, logging omitted):

```text
fn observe_response(ip, path, status, config) -> BehaviorOutcome:
    if !config.enabled || !config.behavior.enabled || allowlisted(ip):
        return empty

    enumeration_enabled = config.behavior.enumeration.enabled
    auth_enabled = config.behavior.auth.enabled
    global_enabled = config.behavior.global_auth.enabled
    is_auth_failure = status in {401, 403} and
                      (auth_enabled or global_enabled) and
                      auth_path_matches(path)

    key = tracking_key(ip, config)
    lock shard[key]
    entry = shard.entries.get_mut(key)
    if entry is None:
        unlock; skip per-source; go to global
    if entry.banned_until is in the future:
        unlock; return empty
    entry.behavior.roll(now, config.behavior.window)

    if enumeration_enabled:
        entry.behavior.requests += 1
        if status == 404:
            norm_path = normalize_path(path)
            if !is_static_asset(norm_path):
                entry.behavior.not_found += 1
                entry.behavior.add_path(norm_path)
    if auth_enabled and is_auth_failure:
        entry.behavior.auth_failures += 1

    if enumeration_enabled and enumeration_conditions_hold(entry) and
       enumeration_flag_unset:
        mark flag; outcome.source = enumeration_flag
        if enumeration.action == BLOCK: apply_ban(entry)
    if auth_enabled and auth_conditions_hold(entry) and auth_flag_unset:
        mark flag; outcome.source = auth_flag
        if auth.action == BLOCK: apply_ban(entry)
    unlock

global:
    if global_enabled and is_auth_failure:
        lock global_auth
        roll window
        global_auth.failures += 1
        if failures >= threshold and !logged:
            logged = true; outcome.global = global_flag
        unlock

    return outcome
```

### 7.2 Outcome type

`ProtectionState::observe_response` returns a small value type so the proxy layer
can log and count without duplicating signal logic:

```rust
pub struct BehaviorOutcome {
    pub source: Option<BehaviorFlag>,
    pub global: Option<GlobalAuthFlag>,
}

pub struct BehaviorFlag {
    pub signal: BehaviorSignal,   // Enumeration | AuthAbuse
    pub action: BehaviorAction,   // Log | Block
    pub requests: u32,
    pub not_found: u32,
    pub distinct_paths: u32,
    pub auth_failures: u32,
    pub ban: Option<Duration>,    // Some when a ban was applied
}

pub struct GlobalAuthFlag {
    pub failures: u32,
    pub window: Duration,
}
```

The proxy layer (`record_behavior` in `src/proxy/server.rs`) maps the outcome to
`warn!` logs and counters. Logging happens after the locks are released.

### 7.3 Ban integration

When the flagging signal's `action` is `BLOCK`:

1. Compute `duration = escalated_duration(ban.duration, ban.max_duration,
   entry.ban_count.saturating_add(1))`.
2. Set `entry.ban_count = entry.ban_count.saturating_add(1)`,
   `entry.banned_until = Some(now + duration)`, `entry.violations = 0`.
3. Reset the behavior entry (`window_start = now`, counters and bitmap cleared,
   flags cleared).
4. Return `BehaviorFlag { ban: Some(duration), .. }`.

The current response is forwarded. The next request from that source reaches
`check_request`, sees `banned_until`, and returns `Decision::Banned`, which maps
to `429 Too Many Requests` with `Retry-After` and the existing
`kunato_banned_total` counter. This is the same lagged behavior as a rate-limit
ban and avoids mutating a response that has already been produced.

When the existing rate limiter applies a ban, it also resets the source's
behavior window. A ban is a natural evaluation boundary: after it expires the
source starts a fresh window instead of inheriting partial counters from before
the ban.

### 7.4 Global signal

A global flag never applies a ban or throttle in this release. It increments a
counter and emits one warning per global window:

```text
WARN behavioral global authentication abuse detected
     failures=... window_secs=... threshold=...
```

The rationale is availability: a global threshold can be reached by an attacker
who wants Kunato to reject authentication traffic. A future release can add an
opt-in `global_auth.action: THROTTLE` that returns `429` only on authentication
paths for a short period, but that needs its own abuse and collateral-damage
analysis.

## 8. Metrics and logs

New Prometheus counters:

| Metric | Meaning |
| --- | --- |
| `kunato_behavior_not_found_total` | `404` observations on non-static paths |
| `kunato_behavior_auth_failures_total` | `401`/`403` observations on authentication paths |
| `kunato_behavior_enumeration_flags_total` | sources flagged for enumeration |
| `kunato_behavior_auth_flags_total` | sources flagged for authentication abuse |
| `kunato_behavior_global_auth_flags_total` | global authentication windows flagged |
| `kunato_behavior_blocked_total` | behavior flags that applied a ban |

The observation counters show overall volume and the flag counters show how
often thresholds fire. Per-source tuning uses the flag logs; operators can also
lower a threshold temporarily while keeping the action at `LOG`. The flag
counters count transitions, not every observed response; the help strings must
say so.

Log lines are deduplicated per source, signal, and window. Include the source
IP, the signal, the observed counts, the configured thresholds, the action, and
the ban duration when one was applied. Include the path only on the
deduplicated flag line (once per window), so an operator can identify what kind
of probe triggered it without turning every `404` into a log line. This matches
the bounded logging used for rule matches.

Example:

```text
WARN behavior threshold reached
     client=203.0.113.7 signal=enumeration path=/admin requests=48
     not_found=44 ratio=0.92 distinct_paths=41 threshold=40 action=LOG
```

The global line is emitted at most once per global window. Repeated bans are
logged by the existing ban path, not by the behavior detector.

A broad scan can still produce one line per flagged source per window. If that
becomes an operational problem, add a process-wide behavior-log budget (for
example, a small token bucket) and count suppressed lines; the metrics remain
exact. This is a follow-up hardening item, not part of the first release.

## 9. Security and false-positive analysis

The trust boundary is the same as the existing protection layer: the source is
the resolved client IP (IPv6-aggregated), and the signal is the upstream's
response status. The direct peer is the default; `client_ip` optionally resolves
a bounded identity assertion from explicitly trusted proxies. Assertions from
untrusted peers are ignored. An attacker who controls the upstream can shape statuses; the detector
is a mitigation layer, not a security invariant, and the rule set plus protocol
limits remain the primary controls.

### 9.1 False positives

| Source of false positives | Mitigation |
| --- | --- |
| Missing static assets, source maps, or favicons | Static path exclusions from the enumeration numerator |
| A SPA or API client that receives many `404`s for optional endpoints | `min_requests`, ratio, distinct-path thresholds; `LOG` default |
| Expired or invalid API tokens (`401` on every API call) | Auth paths are limited to login/token/session/MFA/SSO shapes; a general API `401` does not count |
| Shared NAT or office egress with several failed logins | `auth.min_failures` is above the normal mistype rate; `LOG` default; allowlist trusted egress |
| Legitimate crawlers and link checkers | They are bot-like by definition; `LOG` default and rate limits remain |

Because the default action is `LOG`, a false positive produces a log line and a
metric, not a blocked user. The documentation recommends running in `LOG`
mode for a representative period before setting `BLOCK`.

Deployments behind a CDN or load balancer must configure and verify `client_ip`
before enabling `BLOCK`. Without it, per-source thresholds aggregate unrelated
users and a `BLOCK` action bans the proxy's identity. Follow the
[readiness checklist](behavioral-readiness.md) to verify source separation and
the application's authentication response semantics. NAT clients still share
an identity, and trusted proxy support does not add session/account tracking.

### 9.2 Evasion

- **Distributed sources.** Per-source thresholds are bypassed by spreading
  requests; the global auth window is the intended countermeasure (log-only in
  this release). Distributed enumeration is not detected.
- **IPv6 rotation.** Sources are aggregated by `aggregate_ipv6_prefix` (default
  `/64`), so rotation within one prefix shares counters. A host with a larger
  allocation can rotate prefixes; the global auth window is the backstop, and
  per-source enumeration can still be diluted.
- **Slow probing.** Staying below every window threshold avoids detection. Rate
  limits and the global request guard remain the outer bound.
- **`200`-only scraping.** Opt-in `behavior.scraping` counts distinct `200`
  responses on non-static paths per source and can ban the source. A slow or
  multi-source scraper below the thresholds remains uncovered.
- **Path encoding.** Encoded variants can inflate the distinct-path estimate,
  making detection more sensitive, not less. They cannot hide a `404` from the
  counter.
- **Static-path camouflage.** A scanner can request static assets to dilute the
  enumeration ratio. It must still produce enough distinct `404`s to satisfy the
  distinct-path threshold, and it spends rate budget on the decoy traffic.

### 9.3 Detector as a DoS target

- Per-source state is fixed-size and bounded by `max_tracked_ips`.
- Observation is O(path length) for hashing and O(1) for counters.
- Authentication pattern matching runs only on `401`/`403` responses, not every
  request, and the patterns are compiled at load time with size limits under the
  linear-time `regex` engine.
- No path map, no request body, and no per-path list is retained.
- A missing entry is a no-op; the detector never turns tracking exhaustion into
  a new rejection path.

## 10. Testing

### Unit tests (`src/protection/mod.rs`)

- Enumeration flags only after all three conditions are met.
- A normal mix of `200`s and a few `404`s does not flag.
- Static-asset `404`s do not count toward the numerator but do count in the
  denominator.
- Distinct-path estimation is monotonic and approximately correct for known
  path sets.
- Auth failures flag on the built-in login/token/session paths; a `401` on a
  general API path does not count.
- A custom `auth.paths` list replaces the built-in list.
- Global authentication failures aggregate across synthetic source IPs; a
  per-source threshold is not reached.
- Window rollover resets counters, bitmap, and flags.
- `BLOCK` sets a ban, resets the behavior window, and escalates on a later flag.
- Allowlisted sources and `enabled: false` observe nothing.
- A source with no tracked entry is a no-op.

### Configuration tests (`src/config/mod.rs`)

- The block parses with defaults when omitted.
- Valid custom values parse and compile.
- Invalid window, ratio, distinct-path threshold, failure counts, unknown
  action, invalid regex, and oversized pattern lists are rejected.
- A failed reload preserves the previous compiled configuration (existing
  watcher test pattern).

### Integration tests (`tests/proxy.rs`)

- A mock upstream returning `404` for many distinct paths triggers the
  enumeration counter; with `enumeration.action: BLOCK`, the next request is
  `429` and the upstream access count stops.
- A mock upstream returning `401` on `/login` triggers the auth counter; a `401`
  on `/api/users` does not.
- A rule `BLOCK` response does not increment behavior counters (local responses
  are not observed).
- Behavior observation works over HTTP/1.1 and HTTP/2; HTTP/3 can reuse the same
  mock status if the existing HTTP/3 test harness is available.
- `protection.enabled: false` disables observation.
- Hot reload changes thresholds without losing the active server.

### Black-box suite

The black-box runner starts Kunato with `--disable-protection`, so behavior
detection is intentionally inactive there. The suite cannot assert `LOG`
behavior in any case; integration tests are the authoritative coverage. Do not
add a behavior assertion to `blackbox/requests/` unless the runner grows a mode
that enables protection and expects a ban. Near-miss `allowed.txt` entries for
legitimate `404`/`401` responses are useful guards for any future default change
to `BLOCK`, but they do not exercise the detector today.

## 12. Rollout

1. **Phase 1 (implemented).** Per-source enumeration and auth observation,
   global auth observation, metrics, logs, tests, docs. Default `enabled: true`,
   per-signal `action: LOG`. No traffic is blocked.
2. **Phase 2 (tuning).** Run on a representative deployment, inspect
   `kunato_behavior_*` counters and logs, and adjust defaults. Consider raising
   `enumeration.action` to `BLOCK` only after the false-positive rate is known;
   keep auth `LOG` unless the deployment has a controlled login surface.
3. **Phase 3 (partial).** The opt-in global auth `BLOCK` and `200`-only
   `scraping` signal are available. A challenge, sliding window, configurable
   static exclusions, and account-creation failure bursts remain future work
   because their false-positive and availability tradeoffs differ.

Phase 1 acceptance criteria:

- the configuration parses, validates, rejects invalid patterns, and survives
  hot reload with the previous configuration on failure;
- HTTP/1.1, HTTP/2, HTTP/3, and non-`101` WebSocket handshake responses are
  observed, while local responses, errors, and `101` are not;
- enumeration, per-source authentication, and global authentication flags
  produce the documented logs and `kunato_behavior_*` counters;
- `enumeration.action: BLOCK` bans a source on the next request, escalates on a
  later flag, and resets the behavior window at the ban boundary;
- allowlisted sources, `protection.enabled: false`, and
  `--disable-protection` observe nothing;
- the unit, configuration, and integration tests from Section 10 pass;
- `docs/development.md`, `docs/DESIGN.md`, `rules.example.yaml`, `README.md`, and
  `docs/attack-coverage.md` are updated as described in Section 11.

## 13. Alternatives considered

- **Weighted suspicion score instead of explicit thresholds.** A score hides
  which condition fired and makes the log line hard to explain. Explicit
  counters and thresholds are easier to test, tune, and document.
- **Global ban instead of global log-only.** A global ban is trivially triggered
  by an attacker who wants to deny authentication traffic. The first release
  records the signal and leaves mitigation to per-source bans and the existing
  rate limits.
- **Sliding window instead of tumbling window.** A two-bucket window reduces the
  boundary effect but doubles the counter state and complicates tests. It is a
  reasonable Phase 3 change if operators observe boundary evasion.
- **Boxed behavior state instead of inline.** A `Box<BehaviorEntry>` would keep
  `Entry` small when behavior is disabled, but adds an allocation on the
  response path and an allocator header per tracked source. Inline state is
  simpler and still bounded at roughly 7 MB with the default 100 000-source cap.
- **Per-source action inherited from a single behavior action.** A single action
  cannot raise enumeration to `BLOCK` while leaving authentication in `LOG`
  mode, which is the recommended rollout. Per-signal actions are explicit and
  avoid an inheritance rule.

## 14. Open questions

- Should the enumeration action become `BLOCK` by default after a tuning period,
  or remain opt-in indefinitely?
- What global mitigation is safe against distributed credential stuffing without
  letting an attacker deny authentication to everyone?
- Should a future version use the `WWW-Authenticate` response header to classify
  `401`s outside the configured path list?
- Should a future version count `403`/`400` responses or account-creation
  failures as additional probing signals?
- Is a two-bucket sliding window worth the extra state compared with the
  tumbling window proposed here?
